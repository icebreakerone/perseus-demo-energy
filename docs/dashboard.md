# Perseus sandbox dashboard: user guide

The `perseus-sandbox` dashboard covers the authentication and resource demo apps. `perseus-sandbox-preprod` is the same dashboard for preprod. Both are in CloudWatch in eu-west-2.

Each request that reaches either app writes one audit log line. The line names the client certificate that made the request, the route, and how the request ended. Most widgets are built from these lines. The load balancer widgets and the Athena queries cover connections that never reach an app, because the load balancer refused the client certificate.

The dashboard shows the last 24 hours by default. Change this with the time range picker at the top right. Times are in UTC.

## Request totals

**What it shows:** One panel per app, Authentication and Resource. Each panel counts requests in four groups:

- **Succeeded:** status below 400.
- **Refused:** a 4xx from one of our endpoints.
- **Failed:** a 5xx.
- **Unknown path:** a path or method that no endpoint accepts.

**Useful for:** Checking the health of each app at a glance. A rise in Refused or Failed is worth investigating. Unknown path is nearly all internet scanners and can usually be ignored.

## TLS handshakes refused

**What it shows:** Connections the mTLS load balancers refused before the request reached an app, usually because the client certificate was missing, expired or not trusted.

**Useful for:** Spotting clients who can't connect at all. These clients never appear in the app tables. To see which certificate was refused, use the Athena saved queries (see the last section).

## Requests by outcome

**What it shows:** A graph for each app of Succeeded, Refused and Failed requests in 5-minute intervals. Unknown path requests are left out.

**Useful for:** Seeing when traffic or errors started and stopped. For example, you can match a burst of refusals to a deploy or to a client's test session.

## Who is using what

**What it shows:** Connections to the demo apps that use a client certificate, grouped by application, member, app and route. It also shows the number of requests, how many were refused, and when each was last seen.

**Useful for:** Identifying which members are active and which applications they're using.

## Refused requests by reason and client

**What it shows:** Refused requests counted by the stage where they failed and by client application. The stages are:

- `cert_missing`, `cert_invalid`, `cert_no_application`: problems with the certificate.
- `role`: the certificate lacks the required role.
- `token`, `token_missing`: problems with the access token.
- `permission`: an unknown or expired permission.
- `grant`: a rejected OAuth grant.
- `upstream`: the OAuth provider failed.

**Useful for:** Diagnosing why a particular client is failing, and telling a client exactly what to fix.

## Authorisation activity by client

**What it shows:** Calls to the authentication API's OAuth endpoints (PAR, authorize, token, revoke, permissions), grouped by client application, endpoint and grant type.

**Useful for:** Following a client through the consent and token flow. For example, you can see whether a client is refreshing tokens or keeps starting new authorisations.

## Recent errors

**What it shows:** The 50 latest refused or failed requests. Each row shows the status, error code, failure stage, client application, description and request ID. Unknown path requests are left out.

**Useful for:** Investigating a specific failure. The `request_id` matches the `X-Request-Id` response header, and the `correlation_id` returned on a server error. Search for it in Logs Insights to find every log line for that request.

## Client certificates in use, soonest expiry first

**What it shows:** Each client certificate seen. Columns are the application, member, serial number, issuer, expiry date, days left and last use.

**Useful for:** Contacting members before their certificates expire, and checking which certificate a client is actually using.

## Latency by route

**What it shows:** Request counts with median (p50), p95 and maximum response times in milliseconds, for each app and route.

**Useful for:** Finding slow endpoints, and checking whether slowness is in one route or across the whole app.

## Latency, p95

**What it shows:** The p95 response time for each app over time. This is the time that 95% of requests finish within.

**Useful for:** Seeing whether a slowdown is ongoing or a single spike, and when it began.

## Load balancer: refused handshakes and its own errors

**What it shows:** Refused TLS handshakes on the mTLS load balancers, and 5xx errors generated by any of the four load balancers themselves, over time.

**Useful for:** Finding failures the apps can't log. Examples are a target that is down or timing out, or a sudden wave of bad certificates.

## Resource API Lambda

**What it shows:** Invocations, errors and throttles for the resource API Lambda function, with its p95 duration.

**Useful for:** Telling Lambda problems apart from app errors. Examples are timeouts, cold starts and concurrency limits.

## Further investigation

**Logs Insights:** each table is also a saved query under `Perseus/<env>/`. Use it to change the time range, filter or columns beyond what the dashboard shows.

**Athena:** open Athena in eu-west-2, choose the app's workgroup (for example `perseus-authentication-prod-alb-logs`) and open the Saved queries tab. These queries read the load balancer logs:

- **Refused client certificates, last 7 days:** which certificates the load balancer rejected, and why.
- **Client certificates connecting, last 30 days:** every certificate that completed a handshake.
- **Load balancer errors, last 7 days:** requests the load balancer answered with an error, including Lambda timeouts.
